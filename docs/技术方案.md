## 1. 项目背景与目标

### 1.1 背景

前端开发者同时维护多个 Vue 项目时，需要为每个项目单独开一个终端窗口执行开发命令。现存痛点：

| 痛点 | 具体表现 |
|---|---|
| **窗口管理混乱** | 5 个项目 = 5 个终端窗口，任务栏挤满，难以快速定位 |
| **重启成本高** | 每次重启电脑 / 关闭终端，都要手动 `cd` 到每个项目目录重新敲命令 |
| **状态不可见** | 分不清哪个终端对应哪个项目，日志滚动后无法快速回溯 |
| **停止不干净** | 手动 `Ctrl+C` 后端口仍被占用，导致下次启动端口漂移 |

### 1.2 目标

打造一个**集中式的开发命令管理面板**，实现：

- 一处配置、一处启停：所有项目的开发命令集中管理
- 配置持久化：重启应用后一键恢复所有服务
- 日志聚合查看：每个项目的输出清晰可读，带颜色
- 干净的生命周期管理：停止即彻底释放端口

### 1.3 非目标（明确不做）

范围控制是设计阶段最重要的事。以下明确**不在本期范围**：

| 不做 | 原因 |
|---|---|
| ❌ 完整终端模拟（支持 `vim` / `htop` 等 TUI 程序） | 需求是"跑命令 + 看日志"，不需要伪终端；引入 `node-pty` 会带来原生模块重编译等大量额外成本 |
| ❌ SSH / 远程执行 | 单机场景，不需要 |
| ❌ macOS / Linux 支持 | 先聚焦 Windows，但代码不写死平台判断，为未来预留 |
| ❌ 插件系统 / 脚本 DSL | 需求未验证前不做过早抽象 |
| ❌ 团队协作 / 云端同步 | 无此需求 |

## 2. 技术选型

### 2.1 结论

**主力语言：TypeScript（单一语言贯穿主进程与渲染进程）**

```
Electron（主进程 · Node.js + TypeScript）
        │  IPC
        ▼
Vue 3 + TypeScript（渲染进程）
```

### 2.2 选型依据

本项目的**技术难点不在 GUI，而在 Windows 上的进程与输出流管理**。因此选型的核心标准是：**哪套生态在「Windows 进程管理 + 高吞吐日志流」上最成熟，且开发速度最快。**

| 难点 | 说明 |
|---|---|
| 进程树清理 | `npm run dev` 会派生多层子进程，直接 `kill` 只杀第一层，会留下占端口的孤儿进程 |
| 输出吞吐 | 终端输出是高频小包，IPC 设计不当会导致界面卡顿 |
| 编码处理 | Windows 中文环境下 cmd 输出可能是 GBK，需要处理编码 |
| 回车重写 | 构建进度条用 `\r` 覆盖当前行，不做处理日志会一团乱 |

以上问题在 Node.js 生态中**均有成熟且被大规模验证的解法**。反之，若选用 Rust / C#，这些问题一个都不会消失，却需要用不熟悉的语言重新踩一遍。

### 2.3 候选方案横向对比

| 方案 | 语言 | 进程/终端生态 | 前端开发者上手速度 | 安装包 | 内存占用 |
|---|---|---|---|---|---|
| **Electron + Vue** ✅ | TypeScript | Node.js `child_process`（原生内置） | **最快**：一种语言到底 | ~80–150 MB | ~150–300 MB |
| Tauri 2 + Vue | Rust + TS | 需自行接线 `tokio` 异步 + IPC 流式推送 | 慢：需学 Rust 并处理跨语言调试 | ~5–15 MB | ~60–120 MB |
| Wails + Vue | Go + TS | Go 的进程管理生态较冷门 | 一般 | ~10–20 MB | 中等 |
| WPF / WinUI 3 | C# / XAML | 需自行实现终端输出解析 | 很慢：等于换技术栈 | ~50 MB | 低 |
| Avalonia | C# | 同上 | 很慢 | ~40 MB | 低 |

**决策：Electron。**

关键理由：

1. **分发范围小**（自己 + 团队数人），包体积差异（120MB vs 5MB）不构成实际成本
2. **开发速度是唯一核心指标**，Electron 全链路 TypeScript，无上下文切换
3. **前端代码可迁移**：Vue 部分与框架无关，未来若转为公开产品，只需重写主进程
4. **生态先例充分**：主流终端类桌面应用（Hyper、Tabby、Terminus）均为 Electron 技术栈

|---|---|---|

| `typescript` | `^5.9.3` | registry 上的 TS 7.x 是 **Go 重写版（tsgo）**，而 `vue-tsc` 构建在 TypeScript **5** 的编译器 API 之上，装到 7.x 后 `vue-tsc --noEmit` 无法工作 |

> 其余构建期依赖：`@vitejs/plugin-vue ^6.0.9`、`@types/node ^26.6.3`。

### 2.5 明确排除的依赖

| 排除项 | 理由 |
|---|---|
| ❌ `node-pty` | 需求不需要伪终端。它是 **C++ 原生模块**，代价包括：每次 Electron 升级需 `electron-rebuild`（ABI 不匹配则启动即崩）、需分发预编译二进制、CI 需配置 MSVC 工具链、团队成员 `npm install` 可能失败 |
| ❌ `xterm.js` | 同上。日志视图用 DOM 渲染更可控（可搜索、可复制、可虚拟滚动） |
| ❌ 任何 Rust / C# / Go 组件 | 与技术选型一致 |

> **收益**：本项目实现**零原生依赖**，`npm install` 在任何机器上都能一次成功。

## 3. 系统架构

### 3.1 进程模型

Electron 三层结构，职责严格划分：

```
┌─────────────────────────────────────────────────────────────┐
│  主进程 (Main Process)  ·  Node.js + TypeScript              │
│                                                              │
│  · 应用生命周期（窗口 / 托盘 / 开机自启）                     │
│  · 配置读写（自研 ConfigStore）                                 │
│  · ★ ProcessManager：唯一持有 ChildProcess 句柄的地方         │
│  · ★ LineBuffer：日志的 \r\n 归一化                          │
│  · ★ LogBatcher：日志批量合并后推送                           │
│  · 端口探测与 URL 解析                                        │
└──────────────────────────┬──────────────────────────────────┘
                           │  IPC
┌──────────────────────────┴──────────────────────────────────┐
│  Preload Script  ·  contextBridge                            │
│  · 只暴露白名单 API，不放行 Node 能力                          │
└──────────────────────────┬──────────────────────────────────┘
                           │  window.api.*
┌──────────────────────────┴──────────────────────────────────┐
│  渲染进程 (Renderer)  ·  Vue 3 + TypeScript                   │
│  · 纯 UI，不持有任何进程句柄                                   │
│  · 单例 reactive() store 管理分组树 / 运行时状态 / 日志缓存                   │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 核心设计约束

> **约束 1：进程句柄只能存在于主进程。**

渲染进程**永远不能**直接持有或操作 `ChildProcess`。所有操作（启动 / 停止 / 重启）都是向主进程发指令，状态变更通过事件回推。

**理由**：渲染进程会因 HMR 或页面刷新而重建，若句柄存在渲染侧，刷新即丢失所有进程引用，导致**孤儿进程**（占着端口但无法停止）。

> **约束 2：主进程是状态的唯一真相源（Single Source of Truth）。**

渲染进程的 store 只是主进程状态的**镜像**。任何状态变更都必须先经过主进程，再回推给渲染进程。

**理由**：避免双份状态不一致。例如渲染侧以为"已停止"但主进程认为"运行中"，会导致按钮行为和实际不符。

> **约束 3：安全配置保持默认严格值。**

```ts
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  sandbox: true,
  preload: path.join(__dirname, '../preload/index.js'),
}
```

**理由**：渲染进程只渲染本地数据，无需 Node 能力。保持严格配置可避免日志中的恶意内容（如 `Vite` 输出的用户代码片段）获得执行权限。

## 4. 核心机制设计

### 4.1 进程生命周期管理（★ 本项目第一大难点）

#### 4.1.1 问题

Windows 上执行 `npm run dev` 的真实进程链：

```
cmd.exe  →  node (npm)  →  node (vite)  →  esbuild.exe
```

`child.kill()` **只终止第一层**。后果：

- 界面显示"已停止"，但 `vite` 仍在运行，**占用 5173 端口**
- Vite 检测到端口被占会自动 +1，几轮重启后机器上堆积 5174 / 5175 / 5176 等僵尸进程
- 内存持续增长，且**极难排查**（任务管理器里全是 node.exe）

#### 4.1.2 解决方案

**方案 A：原生 `taskkill`（推荐，无额外依赖）**

```ts
import { spawn } from 'node:child_process'

function killTree(pid: number): Promise<void> {
  return new Promise((resolve) => {
    // /T 终止进程树，/F 强制
    spawn('taskkill', ['/PID', String(pid), '/T', '/F']).on('close', () => resolve())
  })
}
```

**方案 B：`tree-kill` 包**（跨平台封装，API 更简洁）

```ts
import treeKill from 'tree-kill'
treeKill(child.pid, 'SIGTERM', (err) => { /* ... */ })
```

> **建议**：先用方案 A，零依赖；若未来需支持 macOS 再切换到方案 B。

#### 4.1.3 启动方式

**不要用 `shell: true`** —— 命令含空格时会产生引号解析问题。显式调用 shell：

```ts
const child = spawn('cmd.exe', ['/c', 'npm run dev'], {
  cwd: project.path,
  env: {
    ...process.env,
    FORCE_COLOR: '1',        // 强制彩色输出（见 §4.3）
    // 若出现中文乱码，追加：
    // LANG: 'zh_CN.UTF-8',
  },
  windowsHide: true,          // 不弹黑框
  stdio: ['ignore', 'pipe', 'pipe'],
})
```

- `stdio[0]`（stdin）设为 `ignore`：本期不支持交互式输入
- `stdout` / `stderr` 均需监听并合并到同一日志流
- `windowsHide: true`：避免 Windows 上闪出控制台黑框

> **注意**：Vite 等工具检测到 `stdout` 不是 TTY 会自动关闭颜色输出，必须显式设置 `FORCE_COLOR=1`（详见 §4.3）。

#### 4.1.4 状态机

```
                ┌──────────┐
                │   idle   │◄────────────────┐
                └────┬─────┘                 │
                     │ start()               │ taskkill 完成
                     ▼                       │
                ┌──────────┐            ┌────┴─────┐
                │ starting │            │ stopping │
                └────┬─────┘            └────▲─────┘
                     │                       │ stop()
        ┌────────────┴────────────┐          │
        │ 检测到就绪信号           │ spawn 失败│
        ▼                          ▼          │
   ┌──────────┐              ┌──────────┐     │
   │ running  │──────────────│  error   │     │
   └────┬─────┘   进程退出    └──────────┘     │
        │                                      │
        │ stop() / 进程意外退出                 │
        ▼                                      │
   ┌──────────┐                                │
   │  exited  │────────────────────────────────┘
   └──────────┘        (重新 start)
```

**就绪信号检测**（`starting` → `running`）：正则匹配输出流中的本地地址。

```ts
// 覆盖 Vite / Vue CLI / Nuxt / 多数 dev server 的输出格式
/(?:https?:\/\/)?(?:localhost|127\.0\.0\.1|0\.0\.0\.0):(\d{2,5})/i
```

检测到后同时提取端口，用于：

- 界面显示可点击的访问链接（一键用默认浏览器打开）
- 记录实际端口，便于端口冲突排查

> **降级策略**：若 10 秒内未检测到就绪信号，仍然置为 `running`（因为进程确实活着），端口留空。避免因输出格式差异导致状态永远卡在 `starting`。

#### 4.1.5 退出清理

**应用退出时必须终止所有子进程**，否则产生孤儿进程：

```ts
let quitting = false
app.on('before-quit', (event) => {
  if (quitting) return
  event.preventDefault()      // 阻塞退出
  quitting = true
  Promise.all(allPids.map(killTree)).finally(() => app.exit(0))
})
```

同时处理：

| 事件 | 行为 |
|---|---|
| `window-all-closed` | 若开启"最小化到托盘"，则**不退出**；否则退出 |
| `before-quit` | 逐个 `killTree`，全部完成后才真正退出 |
| 渲染进程崩溃 / 刷新 | 无影响（句柄在主进程） |

> **残余风险**：用户从任务管理器强杀进程时无法拦截，会产生孤儿进程。缓解手段见 §9 风险 1。

### 4.2 日志管道（★ 本项目第二大难点）

#### 4.2.1 数据流

```
child.stdout / stderr  (Buffer)
        │  toString('utf8')
        ▼
   LineBuffer           ← \r / \n 归一化（§4.2.2）
        │  LineEvent[]
        ▼
   LogBatcher           ← 时间窗口合并（§4.2.3）
        │  批量 IPC（≤30 次/秒）
        ▼
   渲染进程 store        ← 环形缓冲，上限 N 行（§4.2.4）
        │
        ▼
   LogPanel.vue         ← ANSI → HTML 渲染（§4.3）
```

#### 4.2.2 `\r` 回车重写处理

构建工具的进度条（如 `rendering chunks (3/8)...`）使用 `\r` **覆盖当前行**而不换行。若简单按 `\n` 切分，日志会挤成一团。

**`LineBuffer` 归一化算法**（在主进程执行，`src/main/core/LineBuffer.ts`）：

要处理的是**四种**情况，第四种最容易写错：

1. `\n` 换行 → `append` 新行
2. `\r\n`（Windows）→ 同上，但要先剥掉行尾的 `\r`
3. `\r` 覆写当前行 → `replace` 最后一行（构建进度条就是这么输出的）
4. **`\r` 落在 chunk 末尾 → 必须延迟判定** —— 它可能是 `\r\n` 的前半

第 4 种：若 chunk 恰好切在 `\r` 和 `\n` 之间（`"abc\r"` + `"\ndef"`），立即处理会把 `\r` 当成覆写，导致 `"abc"` 被**误清空**。因此实现里把行尾悬空的 `\r` 暂存到 `carry`，等下一块到了再判定。

```ts
class LineBuffer {
  private lines: string[] = []   // 已提交的完整行（仅为重载重放而保留，有上限）
  private current = ''           // 当前未换行的活动行
  private carry = ''             // 跨 chunk 悬空的内容（只可能是行尾的一个 \r）

  private readonly capacity: number
  constructor(capacity = 1000) {
    // ⚠️ 刻意写成显式字段赋值，而不是 `constructor(private readonly capacity = 1000)`：
    //    Node 的 strip-only 类型擦除不支持 parameter property（那需要*生成*代码），
    //    会直接抛 ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX。
    //    本项目用 `node --test src/**/*.ts` 零构建直接跑单测，这个便利性值得多写两行。
    this.capacity = capacity
  }

  push(chunk: string): LineEvent[] {
    if (!chunk) return []

    let data = this.carry + chunk
    this.carry = ''

    // 行尾悬空的 \r 可能是 \r\n 的前半，推迟到下一块再判定
    if (data.endsWith('\r')) {
      this.carry = '\r'
      data = data.slice(0, -1)
    }
    if (!data) return []

    const events: LineEvent[] = []
    const parts = data.split('\n')

    for (let i = 0; i < parts.length; i++) {
      let seg = parts[i]
      const terminated = i < parts.length - 1   // 非最后一段 = 有 \n 结尾

      // Windows 的 \r\n：先剥掉行尾的 \r，避免被误判成「覆写」
      if (terminated && seg.endsWith('\r')) {
        seg = seg.slice(0, -1)
      }

      const cr = seg.lastIndexOf('\r')
      if (cr >= 0) {
        this.current = seg.slice(cr + 1)        // \r 之后的内容覆盖当前行
        if (!terminated) {
          events.push({ type: 'replace', text: this.current })
          continue
        }
      } else {
        this.current += seg                     // 普通追加
      }

      if (terminated) {
        events.push({ type: 'append', text: this.current })
        this.lines.push(this.current)
        this.current = ''
        this.trim()
      }
    }

    return events
  }

  /** 流结束时调用：提交尚未换行的残留，否则最后一行没有 \n 结尾就会丢 */
  flush(): LineEvent[] {
    const events: LineEvent[] = []
    if (this.carry) {                           // 悬空的 \r：按「覆写为空行」处理
      this.carry = ''
      this.current = ''
      events.push({ type: 'replace', text: '' })
    }
    if (this.current) {
      events.push({ type: 'append', text: this.current })
      this.lines.push(this.current)
      this.current = ''
    }
    return events
  }

  /**
   * 摊还 O(1) 的裁剪：只在超出 capacity + 256 时才批量丢弃。
   * 若每行都做一次 splice(0, 1)，高频日志下每行都要移动整个数组。
   */
  private trim(): void {
    const overflow = this.lines.length - this.capacity
    if (overflow >= 256) this.lines.splice(0, overflow)
  }

  // 另有：snapshot()（副本，供渲染进程重载后重放）、get committed()、
  //       get active()、clear()
}
```

**验证用例**（`src/main/core/LineBuffer.test.ts`，由 `node --test src/**/*.test.ts` 零构建直接跑）：

| 输入 | 期望结果 |
|---|---|
| `"abc\r\ndef"` | `append("abc")` → `append("def")` |
| `"progress 3/8\rprogress 4/8"` | `replace("progress 4/8")` |
| `"line1\nline2\n"` | `append("line1")` → `append("line2")` |
| `"abc"`（无换行） | 无事件（等待后续内容） |
| `"abc\r"` 后跟 `"\ndef"` | `append("abc")` → `append("def")`，**不是** `replace("")` —— 这正是 `carry` 延迟判定的意义 |
| 未换行的残留 + `flush()` | `append(残留)`；若悬空的是 `\r` 则 `replace("")` |
| 行数超过 `capacity + 256` | 批量丢弃溢出部分，缓冲不再增长 |

**行事件类型**：

```ts
type LineEvent =
  | { type: 'append';  text: string }   // 追加新行
  | { type: 'replace'; text: string }   // 替换当前最后一行
```

> **为什么在主进程做归一化**：环形缓冲存的必须是**已定型**的行。若存原始流，渲染进程刷新后重放历史会重现 `\r` 混乱。归一化前置到主进程，历史重放天然正确。

#### 4.2.3 批量推送（背压控制）

Vite 的输出是**突发式**的：启动时可瞬间产生上百个 chunk。若每个 chunk 都发一次 IPC，渲染进程会被淹没。

**`LogBatcher` 设计**：

```ts
class LogBatcher {
  private pending = new Map<string, LineEvent[]>()   // nodeId → 待发送事件
  private timer: NodeJS.Timeout | null = null
  private readonly FLUSH_INTERVAL = 32               // ≈30fps
  private readonly MAX_BATCH = 512                   // 单次批量上限

  enqueue(nodeId: string, events: LineEvent[]) {
    const list = this.pending.get(nodeId) ?? []
    list.push(...events)
    this.pending.set(nodeId, list)
    this.schedule()
  }

  private schedule() {
    if (this.timer) return
    this.timer = setTimeout(() => this.flush(), this.FLUSH_INTERVAL)
  }

  private flush() {
    this.timer = null
    for (const [nodeId, events] of this.pending) {
      // 超量时只保留尾部（最新内容更重要）
      const payload = events.length > this.MAX_BATCH
        ? events.slice(-this.MAX_BATCH)
        : events
      mainWindow.webContents.send(CH.EVT_PROCESS_LOG, { nodeId, events: payload })
    }
    this.pending.clear()
  }
}
```

**效果**：无论输出多快，IPC 频率**恒定在 ≤30 次/秒/命令**，与输出量解耦。

#### 4.2.4 环形缓冲（内存控制）

日志必须有上限，否则长时间运行会导致内存溢出。

| 层面 | 上限 | 说明 |
|---|---|---|
| 主进程 | 每条命令保留一段日志尾巴（`LineBuffer.snapshot()`） | 不缓存完整日志；供渲染进程重载后通过 `log:snapshot` 重放历史 |
| 渲染进程 | **默认 5000 行 / 命令**（`AppSettings.logBufferLines`） | 超出后从头部丢弃，可在设置页调整 |

```ts
function pushLines(store: LogStore, events: LineEvent[]) {
  for (const ev of events) {
    if (ev.type === 'append') {
      store.lines.push({ seq: ++store.seq, text: ev.text, html: '' })
    } else {
      const last = store.lines[store.lines.length - 1]
      if (last) { last.text = ev.text; last.html = '' }   // 置空以触发重新解析
    }
  }
  if (store.lines.length > MAX_LINES) {
    store.lines.splice(0, store.lines.length - MAX_LINES)
  }
}
```

> **`seq` 序列号的作用**：
> 1. 作为 `v-for` 的 `key`（稳定 key 让 Vue 只 patch 新增节点，不重排）
> 2. 渲染进程 HMR 刷新后，可用 `seq` 向主进程请求增量历史，避免重复

### 4.3 颜色与编码处理

#### 4.3.1 强制彩色输出（含 `NO_COLOR` 冲突处理）

Vite / chalk / picocolors 检测到 `stdout` 不是 TTY（通过 `process.stdout.isTTY`）时**会自动关闭颜色**。基础解决方案是设环境变量：

```ts
env: { ...process.env, FORCE_COLOR: '1' }
```

这样无需伪终端即可获得完整的 ANSI 彩色输出。

**⚠️ M0 实测发现的坑：与 `NO_COLOR` 冲突**

验证机上用户环境里**本来就设了 `NO_COLOR`** —— 这是一个跨工具通用的「不要上色」约定。此时若无条件注入 `FORCE_COLOR=1`，Node 会把警告打到 stderr：

```
(node:1948) Warning: The 'NO_COLOR' env is ignored due to the 'FORCE_COLOR' env being set.
```

两个后果：① 每个项目启动时 stderr 多一行警告，**污染日志首屏**；② 更根本地，用户已经显式表达了「不要颜色」，我们却把它覆盖掉了。

**修正后的策略**（已在 `src/main/core/ProcessManager.ts` 落地）：把颜色做成用户可见的开关 `AppSettings.forceColor`，并让开关语义优先于环境：

```ts
if (this.settings.forceColor) {
  // 由本应用接管颜色：清掉外部 NO_COLOR，再注入 FORCE_COLOR
  delete env.NO_COLOR
  env.FORCE_COLOR = '1'
} else {
  // 开关关闭 = 不注入，尊重环境里可能存在的 NO_COLOR
  delete env.FORCE_COLOR
}
```

设置界面在检测到「环境里有 `NO_COLOR` 但用户打开了强制彩色」时展示提示，避免用户困惑为什么日志突然有颜色。

#### 4.3.2 中文编码

Windows 中文环境下，`cmd.exe` 的内置命令输出使用 **GBK（CP936）**，而 Node.js 派生的程序通常输出 UTF-8。混用会导致中文乱码。

**处理策略**：

1. **首选**：启动前切换代码页
   ```ts
   spawn('cmd.exe', ['/c', 'chcp 65001 >nul && npm run dev'], { /* ... */ })
   ```
   > `>nul` 用于抑制 `chcp` 自身的输出

2. **备选**：若特定项目仍乱码，在主进程做编码探测与转码（引入 `iconv-lite`），但会略微增加复杂度

**决策**：先只做方案 1。绝大多数 Vite 项目输出为 UTF-8，`chcp 65001` 已足够。

#### 4.3.3 ANSI 渲染

使用 `ansi_up` 将 ANSI 转义序列转为 HTML span：

```ts
import { AnsiUp } from 'ansi_up'

const ansi = new AnsiUp()
ansi.escape_html = true      // ★ 必须开启
ansi.use_classes = true      // 用 CSS class 而非内联样式，配色才能跟着主题走

export function toHtml(text: string): string {
  const html = ansi.ansi_to_html(text)
  // 只有含 URL 的行才值得做链接化（见 4.3.4）
  return HAS_URL.test(text) ? linkify(html) : html
}
```

> ⚠️ **`escape_html` 必须为 `true`**。Vite 编译错误信息中常出现 `<div>`、`&`、`<>` 等字符，若不转义会破坏 DOM 结构（虽因 `nodeIntegration: false` 不构成严重 RCE 风险，但会导致显示错乱）。

**性能 —— 造行时算一次，结果存进行里**：

```ts
function makeLine(text: string, pending: boolean): RenderLine {
  return { seq: ++seqCounter, text, html: toHtml(text), link: lastUrl(text), pending }
}
```

`store/app.ts` 在把主进程推来的行事件落成 `RenderLine` 时就调用了 `toHtml`，结果连同
`link`（这一行里最后一个 URL）一起存在行上。日志面板只做 `v-html`，不重复解析，也不
每次重渲染都回头扫文本 —— 5000 行 / 命令的上限下，任何「每帧重算」都撑不住。

#### 4.3.4 日志里的可点击链接

dev server 启动后打出的 `http://localhost:5173/` 应当能直接点开，否则用户得手动切到
浏览器再敲一遍地址 —— 而这正是本工具最高频的一个动作。

**渲染**（`src/renderer/src/utils/ansi.ts`）：在 `ansi_up` 转义**之后**，按
`/<[^>]*>|[^<]+/g` 把 HTML 切成「标签」与「文本」交替的片段，只对文本片段做 URL 匹配。
安全边界因此没有移动 —— 日志内容早在 `escape_html` 那一步就已是纯文本，而替换决不触碰
任何 `<...>` 片段。反过来的两种写法都不行：先替换再转义会把自己生成的标签也转义掉；对
整段 HTML 直接跑正则则可能命中标签内部的属性。

匹配的是**已转义**的文本，所以正则写成 `https?:\/\/(?:&amp;|[^\s<>"'`&])+` —— 那里出现的
`&` 一定是某个实体的一部分（真 `&` 早已变成 `&amp;`）。只放行 `&amp;` 是为了让一句被转义的
`<a href="http://evil/">` 不会让 URL 一路吃掉后面整个 `&quot;&gt;…` 尾巴。行尾标点
（`. , ; : ! ? ) ] }` 与中文标点）留在链接之外。

另有便宜的先验 `HAS_URL`：绝大多数日志行根本没有链接，不值得为它们做切片。

**点击**：产出的是 `<a class="log-link" data-url="…">`，**没有 `href`**。渲染进程里一个真的
`href` 被点中会把**整个应用窗口**导航到那个地址，界面上就再也回不来了。所以点击由
`LogPanel.vue` 在视口上委派处理（`@click` → `closest('.log-link')` → 取 `dataset.url`），
再走 IPC 交给系统浏览器。

**主进程白名单**（`src/main/ipc/index.ts` 的 `shell:openUrl`）：这些 URL 现在可以直接来自被
监控进程的输出，等于不可信输入 —— `shell.openExternal` 会把**任意协议**交给系统上注册的
处理器，`file:` 能打开本地文件、自定义协议能拉起别的程序。因此只放行 `http:` / `https:`，
其余抛错回渲染层（显示成红色横幅 `banner error`）。

**头部入口**：日志面板头部在检测到链接时显示一个「↗ localhost:5173」按钮。Vite 把地址打在
第一屏，之后就被成千上万行输出顶走，靠肉眼往回翻不现实；按钮取的是最近一行带 `link` 的
值（反向扫一遍读字段，不重扫文本）。

**卡片上的入口**：头部只放得下「最近一个」，所以命令卡片上另有一个 `🔗 N` 下拉，列出这条
命令输出里出现过的**全部**地址供挑选 —— 一条命令同时开多个端口时（前端 + mock 服务、
monorepo 各子包），只给一个入口是不够的。见附录 D.3。

**只认被监控进程的真实输出**：候选来自日志行的 `link` 字段，而这个字段对
`[terminal-manage]` 开头的行**恒为 `null`**。原因是启动横幅会把命令行原样回显 ——
`curl http://内网/health`、`vite --host http://…` 这类命令，其**文本**里的地址会被算成
「这条命令暴露的链接」，用户点开看到一个根本没人监听的地址，这比没有链接更误导人。
判据抽在 `src/shared/log.ts`（`META_PREFIX` + `isMetaLine()`）：主进程用它拼接自己插的每一行
（横幅 / 退出提示 / 端口警告 / 终止通知，全部经由 `ProcessManager.logDirect`），渲染层的
`linkOf()` 用同一个常量过滤。**共用常量而不是两边各写一遍字面量** —— 后者在前缀改动的
那一天必然有一边静默失效，而下拉里多出几条假链接是没有任何报错的。
附带结论：命令在「运行中」之前不会有链接，因为工具自己的行不产生链接，而真实输出
只可能来自一个已经跑起来的进程。

> **不要**在每次日志更新时对整个数组重新执行 `ansi_to_html`，否则 3000 行的项目会明显卡顿。

### 4.4 持久化与恢复

#### 4.4.1 核心原则

> **不要保存进程状态，只保存声明式配置。**

进程是运行时对象，无法序列化。持久化的应是"**要运行什么**"，而非"**正在运行什么**"。

App 启动时读取配置 → 逐个 spawn → 即实现了"重启电脑后不用重新敲命令"的核心诉求。

#### 4.4.2 恢复策略：不自动拉起，只记住「要跑什么」

```ts
// 应用启动时**不**自动拉起任何命令，只把配置读进内存。
// 拉起谁完全由用户点「启动已标记」时决定：
const specs = collectMarkedSpecs(store)   // = collectSpecs(store, (node) => node.marked)
await processes.startAll(specs)           // 内部串行启动，间隔 settings.launchDelayMs
```

**为什么刻意不再自动拉起**：打开这个工具时，用户往往只想看日志、改一行配置、或者停掉某个跑飞的服务 —— 此时十几个 dev server 一起抢 CPU 和端口，只会让工具自己启动变慢、日志面板瞬间被刷满。更麻烦的是，它们与手点「启动已标记」拉起的那批进程混在一起，事后说不清哪个是谁起的。「重启电脑后不用重新敲命令」这个原始诉求由**一次点击**满足：标记过的命令会被记住，点一下全起来（见 §4.4.4）。

**为什么要串行 + 延迟**：5 个 Vite 项目同时启动会产生剧烈的 CPU / 磁盘抢占，反而每个都变慢，且日志交错难以阅读。串行启动视觉上更清晰，总耗时通常更短。

**优雅降级**：

| 情况 | 处理 |
|---|---|
| 项目目录不存在（被删除 / 移动） | 标记为 `error`，日志提示"路径不存在"，**跳过**且不阻塞其他项目 |
| `package.json` 不存在 | 同上，提示可能不是 Node 项目 |
| 启动后 10s 无就绪信号 | 仍标记 `running`（进程存活），端口留空 |
| 启动后立即退出（code ≠ 0） | 标记 `exited`，显示退出码，**不自动重试**（避免无限重启循环） |

#### 4.4.3 配置文件位置

由自研 `ConfigStore`（`src/main/store/config.ts`，零依赖）管理，路径：

```
%APPDATA%\terminal-manage\config.json
```

写入采用**临时文件 + rename 的原子写**，避免断电 / 崩溃时留下半截 JSON。

**必须包含版本号**，便于 schema 迁移。当前 `CONFIG_VERSION = 2`：

```json
{
  "version": 2,
  "nodes": [ /* GroupNode | CommandNode —— 扁平数组 + parentId */ ],
  "settings": { /* AppSettings */ }
}
```

v1 → v2 迁移（`migrateFromV1`）：旧配置里的每个项目转成**一个绑定目录的分组 + 一条命令**。刻意不按旧的分组名合并 —— 合并会丢掉 `path`；旧 `cwd` 与 `path` 不一致时记 warning 并丢弃 `cwd`。

设置的读取（`mergeSettings`）**逐字段校验类型**，而不是 `{ ...DEFAULT_SETTINGS, ...raw }`：配置文件是用户可见、可以手工编辑的，展开合并会让一个手写的 `null` 悄悄覆盖掉默认值。

#### 4.4.4 命令标记（`marked`）：决定点「启动已标记」时拉起谁

一条命令是「常驻的」还是「偶尔手动跑一下」，只由 `CommandNode.marked` 这一个布尔字段表达：

| 标记状态 | 点「启动已标记」时 |
|---|---|
| 已标记（★） | 会被一起拉起 |
| 未标记（☆） | 不动它，停在「未启动」 |

**判据只有一处实现**，在 `src/main/ipc/index.ts`：

```ts
export function collectMarkedSpecs(store: ConfigStore): SpawnSpec[] {
  return collectSpecs(store, (node) => node.marked)
}
```

渲染层的「启动已标记」按钮与托盘菜单的「启动已标记的命令」都走它。两边各写一遍 `node.marked` 的代价不是重复，而是**将来判据一变，静默走偏的那一侧表现为「点了启动已标记，有些该起来的没起来」** —— 没有异常、没有日志、只有一个说不清的现象。

判据的两条隐含语义：

- **看整棵树**，不只是当前选中的分组 —— 用户标记的是「我平时要跑的命令」，与他此刻在看哪一层无关。
- **不管隐藏与否** —— 隐藏只是不想让它占地方，被标记的命令照样该跑（`collectSpecs` 的 `includeHidden` 固定为 `true`）。

**入口有四处**（写的是同一份数据）：① 卡片头最右端的星标（☆ ↔ ★，**常驻显示**，最直接的一处）② 命令行 / 卡片的 `⋯` 菜单 →「标记为常驻命令」③ 命令弹窗里的「标记为常驻命令 —— 点『启动已标记』时会一起启动」勾选框 ④ 新建命令时同样可以勾。卡片区标题行显示**这一层**的标记数（形如 `8 条命令 · 1 隐藏 · 1 已标记`），「启动已标记」按钮的悬停提示显示**全局**标记数 —— 因为真正被拉起的就是全局那批。

**一条都没标记时不做「无操作的成功」**：按钮不禁用（禁用的按钮不解释自己为什么禁用，就是哑故障），而是弹一句提示「还没有标记任何命令 —— 点卡片右上角的 ☆ 标记要随『启动已标记』一起跑的命令」。托盘菜单做不到动态文案，所以把判据写进了标签：「启动已标记的命令」。

**这对按钮是刻意不对称的**：「启动已标记」只挑 `marked` 的那批，紧邻的「全部停止」却收掉**所有**在跑的进程 —— 包括用户一条条手点起来的。两者用途不同：启动是「把我标记的常驻命令一次带起来」；停止是**急停**（服务跑飞、端口被占、风扇狂转时，用户不会去分辨哪条是标记过的，他要的是立刻全停）。若停止也只停已标记的，急停就会留下几条没标记的孤儿继续占端口 —— 那恰好是这个工具最初想解决的问题。托盘菜单同样是这个分法。

**为什么用星标而不是给整张卡片染色**：卡片底色已经被运行状态占满了（running 绿 / busy 琥珀 / error 红），再叠一套标记色只会互相淹没。同理 ★ 用强调色而不是金色 `--warn` —— 金色在这套界面里已经表示「启动中 / 停止中」，一颗金星星会被误读成「这条正忙」。

**v2 → v3 的字段改名**：这个字段在 v2 里叫 `autoStart`，含义是「应用启动时自动拉起」。语义整个换掉之后名字必须跟着换 —— 继续叫 `autoStart` 会骗下一个读代码的人（既没有「自动」，也没有「随应用启动」）。老配置的兼容读取放在 `src/shared/tree.ts` 的 `normalizeTree()` 里：

```ts
marked: rec.marked === true || rec.autoStart === true
```

两个键都认，于是 v2 里勾过的命令不会在升级后突然变成未标记（那些正是用户「平时都要跑」的），写回时只写 `marked`。因此 `ConfigStore.migrate()` 不需要额外的迁移分支。

### 4.5 端口管理（增强功能）

#### 4.5.1 端口冲突预检

启动项目前，若配置了预期端口，先检查该端口是否被占用：

```ts
function isPortInUse(port: number, host = '127.0.0.1'): Promise<boolean> {
  return new Promise((resolve) => {
    const srv = net.createConnection({ port, host })
    srv.once('connect', () => { srv.destroy(); resolve(true) })
    srv.once('error', () => resolve(false))
    srv.setTimeout(300, () => { srv.destroy(); resolve(false) })
  })
}
```

若被占用则提示用户：

> ⚠️ 端口 5173 已被占用，可能是其他项目或残留进程。[查看占用进程]

#### 4.5.2 残留进程排查

提供辅助能力：查询某端口的占用进程 PID，方便用户清理历史残留。

```ts
// netstat -ano | findstr :5173   →  解析出 PID
// tasklist /FI "PID eq <pid>"     →  显示进程名
```

> **定位**：这是**排障辅助功能**，不是核心。已在 `src/main/core/PortScanner.ts` 落地，通过 `port:check` 通道暴露，并在启动前配合 `CommandNode.expectedPort` 做占用提示。

### 4.6 命令发现（读取 `package.json`）

「自动读命令」由 `src/main/core/PackageReader.ts` 独立完成。它是一个**纯 Node 模块，不依赖 Electron**，因此可以被 `node --test` 直接驱动。

```ts
export async function readPackageInfo(inputDir: string, withWorkspaces = true): Promise<PackageInfo>
export function scriptToCommand(packageManager: PackageManager, key: string): string   // → `${pm} run ${key}`
export function defaultGroupName(info: Pick<PackageInfo, 'name' | 'dir'>): string
```

#### 4.6.1 包管理器探测顺序

1. 先读 `package.json` 的 `packageManager` 字段（corepack 约定），并能剥掉 `pnpm@9.1.0` 这类版本号；
2. 否则按锁文件判定，顺序固定：

| 锁文件 | 判定结果 |
|---|---|
| `pnpm-lock.yaml` | `pnpm` |
| `yarn.lock` | `yarn` |
| `bun.lockb` / `bun.lock` | `bun` |
| `package-lock.json` | `npm` |

**子包自己没有锁文件**，所以要向上最多 5 层去找仓库根的锁文件 —— monorepo 里 `packages/foo` 用哪个包管理器，实际由仓库根决定。

`scriptToCommand()` 一律生成 `<pm> run <key>`，**不省略 `run`**：省略写法各家行为不一致，且可能撞上同名内建命令被抢走。

#### 4.6.2 workspaces 展开

**同时读 `package.json#workspaces` 与 `pnpm-workspace.yaml`** —— pnpm 只认后者，漏掉它 monorepo 会一个子包都展开不出来。

通配匹配支持：

- 字面路径（`packages/foo`）
- `*`（单层）与 `**`（递归）
- **段内通配**（如 `internal-*`）—— 用 `segmentToRegExp` 编译，带 `i` 标志，因为 **Windows 文件名不区分大小写**
- `!` 前缀表示排除

遍历时跳过 `SKIP_DIRS`（`node_modules`、`.git`、`.hg`、`.svn`、`dist`、`out`、`.next`、`.nuxt`、`coverage`），递归深度上限 `MAX_GLOB_DEPTH = 6`。

每个命中的目录都会单独读一次 `package.json` 取 `name` 与 `scripts`，缺 `name` 时退回目录名。

#### 4.6.3 容错

- **目录不存在 / 不是目录**：返回 `{ found: false, packageManager: 'npm', scripts: [], workspaces: [], warnings: ['目录不存在或不是目录：…'] }`，**不抛异常** —— 用户选错目录是很常见的事。
- **`package.json` 语法错误**：`readJsonObject` 只记一条 `warnings`，界面直接展示给用户，其余能读到的部分照常使用。

### 4.7 主题（浅色 / 深色 / 跟随系统）

用户可选 `AppSettings.theme = 'dark' | 'light' | 'system'`（默认 `dark`）。**换色的落点只有一个：主进程。**

```ts
// src/main/theme.ts
export function applyThemeSource(theme: ThemeMode): void {
  nativeTheme.themeSource = theme // Chromium 据此决定渲染进程的 prefers-color-scheme
}
```

渲染层**一行主题代码都没有**：不往 DOM 上挂 `data-theme`、不在 Vue 里存一份状态、也不需要主进程发「请重绘」的通知。整条链路是：

```
设置弹窗保存 → IPC setting:update → store 落盘
             → nativeTheme.themeSource = 'light'
             → 渲染进程 prefers-color-scheme 重新求值
             → styles.css 里的 @media 自动生效
```

**为什么不让渲染层主导**（在 `<html>` 上切一个 class）：那样必须先把主题通过 IPC 推给渲染进程、再由 Vue 写 DOM，于是必然出现「首帧还不知道主题」的空窗 —— 用户每次启动都会看到一次错误颜色闪一下。走 `nativeTheme` 这条路，媒体查询在样式解析期就求值完了，没有这个窗口期。

CSS 的写法（`src/renderer/src/styles.css`）：

- `:root` 里放**深色**取值作为默认，`@media (prefers-color-scheme: light) { :root { … } }` 整块覆盖成浅色。
- 两个块里都要写 `color-scheme: dark` / `color-scheme: light`。**不能省** —— 少了它会得到「浅色界面 + 深色原生滚动条和复选框」这种半拉子结果，因为滚动条、`<select>` 下拉、复选框都是浏览器自己画的，只认 `color-scheme`。
- 连 **ANSI 调色板也是变量**（`--ansi-red-fg` 等 32 个），所以「亮色终端配色放在浅色界面上糊成一片」的问题在主题层就解决了，`ansi_up` 产出的 HTML 一个字都不用改。
- 日志区单独一个 `--log-bg`：浅色下别的面板是灰底、日志区是纯白，读起来更像一张纸。

窗口底色（`backgroundColor`）必须与 `--bg` 保持一致，否则在页面尚未渲染、以及缩放和拖动窗口时的空隙里会闪出另一种颜色。因此：

- 启动时在 `bootstrap()` 里、`createWindow()` **之前**调 `applyThemeSource(store.settings.theme)`，让首帧就用对颜色；
- 运行中改主题时，在 `setting:update` 处理器里调 `applyThemeSource` + `refreshWindowBackgrounds()`（后者遍历所有窗口 `setBackgroundColor`），免得切到浅色后页面之外还留着一圈深色边框。

**这条链断掉时的症状极其隐蔽**：界面毫无反应、不报错、日志里也看不出任何线索，用户只会觉得「这个选项是坏的」。所以 `npm run test:ui` 里专门加了一条断言（§8）—— 它和 §7 附录 B 里那些界面缺陷属于同一类：**必定发生，但完全静默**。

## 5. 数据模型

### 5.1 持久化模型：可嵌套的分组树

整棵树以**扁平数组 + `parentId` 指针**存储，而不是嵌套对象 —— 移动一个子树、重排同级、改父节点，都只是改一个指针加一个 `order`，不需要深拷贝。嵌套结构在这些操作上极易写错。

```ts
type ShellKind = 'cmd' | 'powershell'

interface NodeBase {
  id: string
  parentId: string | null          // null = 根级
  order: number                    // 同一父节点下的排序，升序
  createdAt: number
  updatedAt: number
}

/** 分组：树里唯一的容器 */
interface GroupNode extends NodeBase {
  kind: 'group'
  name: string
  path?: string                    // 绑定的项目目录绝对路径；留空则继承父分组
  expanded: boolean                // 展开状态持久化，省得每次重启都要重新点开
}

interface CommandNode extends NodeBase {
  kind: 'command'
  name: string                     // ★ 用户可编辑的展示名，如「前端开发服务器」
  script?: string                  // 来源 script 的 key（如 dev）；手工创建的命令没有此项
  command: string                  // 真正执行的命令行，如 pnpm run dev
  autoDiscovered: boolean          // 由 package.json 自动发现且用户没改过
  missing?: boolean                // 来源 script 已从 package.json 消失
  hidden: boolean                  // 隐藏后不在树中渲染，只能在设置页看到
  marked: boolean                  // 标记为「常驻」：点「启动已标记」时会被一起拉起（见 §4.4.4）
  shell: ShellKind
  env?: Record<string, string>
  expectedPort?: number            // 预期端口，用于启动前冲突预检
  color?: string
}

type TreeNode = GroupNode | CommandNode
```

**核心设计：`GroupNode.path` 是「项目目录」的唯一载体。** 命令自己不存路径，执行目录 = 沿 `parentId` 往上找最近的带 `path` 的祖先：

```ts
// src/shared/tree.ts
export function resolvePath(nodes: TreeNode[], nodeId: string): string | null
```

这样在左树上拖动一个分组，它下面几十条命令的 cwd 会全部跟着走，不会出现「命令还指着旧目录」的错位。**「这条命令到底在哪个目录跑」的唯一答案来源就是 `resolvePath()`。**

分组**允许没有 `path`** —— 这样「纯分类用的文件夹」（把几个项目归到「公司项目」下）和「项目目录」是同一种节点，不必引入两套概念。

`autoDiscovered` 这个标记不只是界面上的装饰，它**决定了「重新扫描」会不会碰这张卡片**：重新扫描只认领自动派生的卡片，**手动建的卡片一律不碰**（不置灰、不删除）—— 它不是从 `scripts` 派生出来的，没有「脚本消失」这个概念。

**为什么 `missing` 的节点刻意不删**：这个节点上可能已经有用户起的名字、隐藏设置、`marked` 标记。因为一个 script 临时改名就把这些都扔掉，代价远大于在树上留一条灰条。

```ts
interface AppConfig {
  version: number                  // 当前 CONFIG_VERSION = 3
  nodes: TreeNode[]
  settings: AppSettings
}

interface AppSettings {
  theme: 'dark' | 'light' | 'system'
  logBufferLines: number           // 每条命令的日志上限，默认 5000
  minimizeToTray: boolean          // 关闭窗口时最小化到托盘
  autoLaunch: boolean              // 开机自启
  launchDelayMs: number            // 批量启动时命令之间的间隔，默认 400（毫秒）
  fontSize: number                 // 日志字号，默认 12
  forceColor: boolean              // 强制彩色输出，默认 true（见 §4.3.1）
  showHiddenCommands: boolean      // 树里是否显示已隐藏的命令，默认 false
  splitRatio: number               // 右侧上下分栏比例，默认 0.45，夹在 0.15–0.85
}
```

> `splitRatio` 存的是**比例而不是像素**：窗口大小变化、换显示器之后像素值会变得毫无意义，比例不会。

`showHiddenCommands` 是「隐藏」功能的兜底开关 —— 没有它，用户把一条命令藏进一个收起的、没绑目录的分组之后，就再也找不到入口把它放出来。日常的隐藏 / 取消隐藏在「编辑命令可见性」弹窗里逐条勾选（见 D.6），这个开关只负责「把已隐藏的也显示出来」。

### 5.2 树操作（纯函数，`src/shared/tree.ts`）

树操作全部是纯函数，且**放在 `shared/` 而不是 `main/`** —— 不依赖 Electron 才能被 `node --test` 直接跑。

| 函数 | 作用 |
|---|---|
| `findNode(nodes, id)` | 按 id 取节点 |
| `isGroup(node)` / `isCommand(node)` | 类型收窄 |
| `childrenOf(nodes, parentId)` | 取直接子节点，按 `order` 升序（同序退回 `createdAt`） |
| `descendantIds(nodes, id)` | BFS 取全部后代；带 `visited` 集合防环死循环 |
| `isDescendantOf(nodes, candidateId, ancestorId)` | 判断祖先关系（含自身）；**移动前必查**，否则子树会从树上脱落 |
| `moveNode(nodes, dto)` | 移动 + 重排，返回新数组 |
| `removeWithDescendants(nodes, id)` | 删节点并返回被连带删除的 id 列表 |
| `resolvePath(nodes, nodeId)` | ★ 向上找最近的带 `path` 的分组 |
| `collectCommands(nodes, parentId, opts)` | 聚合某分组下的命令（含后代），用于批量启动 |
| `normalizeTree(nodes, warnings)` | 加载时清洗 |

`normalizeTree()` 的取舍值得单说：遇到非法 `kind`、重复 `id` 会丢弃；但**父指针指向不存在的节点、指向一个命令、或父子关系成环时，一律把该节点提升到根级，而不是丢弃** —— 节点上的命令配置是用户手工调过的，宁可位置不对也不能消失。

### 5.3 运行时模型（**不持久化**，仅存于内存）

```ts
type ProcessStatus =
  | 'idle'       // 未启动
  | 'starting'   // 已 spawn，等待就绪信号
  | 'running'    // 运行中
  | 'stopping'   // 正在执行 kill
  | 'exited'     // 已退出（正常或异常）
  | 'error'      // 启动失败

interface RuntimeState {
  nodeId: string                   // ★ 命令节点 id —— 只有命令会被 spawn，分组没有运行时状态
  status: ProcessStatus
  pid?: number
  exitCode?: number | null
  signal?: string | null
  startedAt?: number
  detectedPort?: number            // 从日志中解析出的实际端口
  lastError?: string
  stoppedByUser?: boolean          // 区分「用户主动停止」与「意外崩溃」
}
```

**`SpawnSpec` 是进程管理与数据模型之间的隔离层：**

```ts
interface SpawnSpec {
  id: string                       // 命令节点 id，作为运行时状态的 key
  label: string                    // 日志首行的展示名
  command: string                  // 实际执行的命令行
  cwd: string
  shell: ShellKind
  env?: Record<string, string>
  expectedPort?: number
}
```

`ProcessManager` **只认 `SpawnSpec`，完全不认识树**。「cwd 从哪个祖先分组继承」这类业务判断全部留在 ipc 层（`collectSpecs()`）。好处是进程管理可以独立于数据模型演进，也能被集成测试直接驱动而不必先造一棵树。

## 6. IPC 接口设计

### 6.1 约定

| 方向 | 机制 | 用途 |
|---|---|---|
| 渲染 → 主 | `ipcRenderer.invoke` / `ipcMain.handle` | 请求-响应（带返回值） |
| 主 → 渲染 | `webContents.send` / `ipcRenderer.on` | 事件推送（单向） |

### 6.2 通道清单

通道常量集中在 `src/shared/channels.ts` 的 `CH` 对象里，主进程与渲染进程共用，避免魔法字符串。

**树（`tree:*`）** —— 入参里的 id 一律是**节点 id**；只有命令节点会被 spawn，分组没有运行时状态。

| 通道 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `tree:list` | — | `TreeNode[]` | 取整棵树的扁平数组 |
| `tree:createGroup` | `GroupCreateDTO` | `GroupNode` | 新建分组（可带 `path`） |
| `tree:createGroupFromDir` | `GroupFromDirDTO` | `GroupFromDirResult` | ★ 导入目录：建分组 + 可选展开 workspaces + 可选导入 scripts |
| `tree:createCommand` | `CommandCreateDTO` | `CommandNode` | 手动新建命令卡片 |
| `tree:update` | `NodeUpdateDTO` | `TreeNode` | 改名 / 改命令 / 隐藏 / 改预期端口 / 折叠 |
| `tree:delete` | `id: string` | `string[]` | 删除节点，返回被连带删除的 id 列表（删分组会带走整个子树） |
| `tree:move` | `MoveNodeDTO` | `boolean` | 移动 + 重排 |

```ts
interface GroupCreateDTO     { parentId: string | null; name?: string; path?: string }
interface GroupFromDirDTO    { parentId: string | null; dir: string; name?: string;
                               expandWorkspaces: boolean; importScripts: boolean }
interface GroupFromDirResult { group: GroupNode; createdCommands: number;
                               createdGroups: number; warnings: string[] }
interface CommandCreateDTO   { parentId: string; name?: string; command: string; script?: string;
                               shell?: ShellKind; env?: Record<string, string>;
                               marked?: boolean; expectedPort?: number; color?: string }
interface NodeUpdateDTO      { id: string; name?: string; path?: string; expanded?: boolean;
                               command?: string; shell?: ShellKind; env?: Record<string, string>;
                               marked?: boolean; hidden?: boolean;
                               expectedPort?: number; color?: string }
interface MoveNodeDTO        { id: string; newParentId: string | null; index: number }
```

`tree:createGroup` 只返回一个 `GroupNode`，而 `tree:createGroupFromDir` 返回 `GroupFromDirResult`（带 `createdCommands` / `createdGroups` 计数与 `warnings`）—— 一次导入可能连带创建几十个节点，界面需要知道总共建了什么、以及哪些子包没读成功。

**package.json**

| 通道 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `pkg:inspect` | `dir: string` | `PackageInfo` | 只读探测，不建任何节点（新建项目弹窗里选完目录即时预览） |
| `pkg:rescan` | `groupId: string` | `RescanResult` | 重新扫描某分组，增量修正自动派生的卡片 |

```ts
interface RescanResult {
  added: number         // 新增的命令数
  newlyMissing: number  // 因 script 消失而被标记 missing 的数量
  restored: number      // 因 script 回归而解除 missing 的数量
  updated: number       // 命令内容被自动跟随刷新（仍是 autoDiscovered）的数量

}
```

|---|---|---|

### 6.3 Preload 暴露的 API

preload 用 `contextBridge` 暴露 `window.api`，它是渲染层**唯一**的通信入口。主进程的处理器统一返回 `{ ok: true, data }` / `{ ok: false, error }` 信封，由 preload 拆包成「正常返回 / 抛 Error」，渲染层因此可以直接 `try / catch`：

```ts
// src/preload/index.ts（节选）
import { CH, EVENT_CHANNELS } from '@shared/channels'

async function invoke<T>(channel: string, ...args: unknown[]): Promise<T> {
  const raw: unknown = await ipcRenderer.invoke(channel, ...args)
  if (raw !== null && typeof raw === 'object' && 'ok' in raw) {
    const envelope = raw as { ok: boolean; data?: unknown; error?: string }
    if (!envelope.ok) throw new Error(envelope.error ?? '主进程返回了未知错误')
    return envelope.data as T
  }
  return raw as T
}

const api = {
  tree: {
    list: () => invoke(CH.TREE_LIST),
    createGroup: (dto) => invoke(CH.TREE_CREATE_GROUP, dto),
    createGroupFromDir: (dto) => invoke(CH.TREE_CREATE_GROUP_FROM_DIR, dto),
    createCommand: (dto) => invoke(CH.TREE_CREATE_COMMAND, dto),
    update: (dto) => invoke(CH.TREE_UPDATE, dto),
    remove: (id) => invoke(CH.TREE_DELETE, id),
    move: (dto) => invoke(CH.TREE_MOVE, dto),
    rescan: (groupId) => invoke(CH.PKG_RESCAN, groupId),
  },
  pkg:    { inspect: (dir) => invoke(CH.PKG_INSPECT, dir) },
  processes: {
    start: (id) => invoke(CH.PROCESS_START, id),
    stop: (id) => invoke(CH.PROCESS_STOP, id),
    restart: (id) => invoke(CH.PROCESS_RESTART, id),
    startAll: () => invoke(CH.PROCESS_START_ALL),
    stopAll: () => invoke(CH.PROCESS_STOP_ALL),
    snapshot: () => invoke(CH.PROCESS_SNAPSHOT),
  },
  logs:     { snapshot: (id) => invoke(CH.LOG_SNAPSHOT, id), clear: (id) => invoke(CH.LOG_CLEAR, id) },
  settings: { get: () => invoke(CH.SETTING_GET), update: (patch) => invoke(CH.SETTING_UPDATE, patch) },
  shell:    { openPath: (t) => invoke(CH.SHELL_OPEN_PATH, t), openUrl: (u) => invoke(CH.SHELL_OPEN_URL, u), pickDir: () => invoke(CH.SHELL_PICK_DIR) },
  port:     { check: (port) => invoke(CH.PORT_CHECK, port) },
  env:      { info: () => invoke(CH.ENV_INFO) },
  on: (channel, listener) => { /* 见下 */ },
}

contextBridge.exposeInMainWorld('api', api)
```

事件订阅 `on()` 做两件事：

1. **白名单校验** —— `if (!EVENT_CHANNELS.includes(channel))` 直接拒绝，只放行上面列出的 5 个事件通道，渲染层订阅不到任何内部通道；
2. **返回取消订阅函数** —— 否则 Vue 组件卸载后回调仍持有 store 引用，造成内存泄漏。

> 完整的类型契约在 `src/shared/api.ts` 的 `TerminalManageApi`；渲染层通过 `src/preload/index.d.ts` 拿到 `window.api` 的类型。

## 附录 A：M0 可行性验证脚本

> 在正式开发前，用此脚本验证地基。**必须确认最后一步端口已释放。**

```js
// spike.js  ——  node spike.js
const { spawn } = require('node:child_process')
const net = require('node:net')

const TARGET = process.argv[2] || process.cwd()
const PORT = 5173

const child = spawn('cmd.exe', ['/c', 'chcp 65001 >nul && npm run dev'], {
  cwd: TARGET,
  env: { ...process.env, FORCE_COLOR: '1' },
  windowsHide: true,
  stdio: ['ignore', 'pipe', 'pipe'],
})

child.stdout.on('data', (d) => process.stdout.write('[OUT] ' + d))
child.stderr.on('data', (d) => process.stderr.write('[ERR] ' + d))

function isPortInUse(port) {
  return new Promise((resolve) => {
    const s = net.createConnection({ port, host: '127.0.0.1' })
    s.once('connect', () => { s.destroy(); resolve(true) })
    s.once('error', () => resolve(false))
    s.setTimeout(500, () => { s.destroy(); resolve(false) })
  })
}

setTimeout(async () => {
  console.log('\n=== 端口占用检查（应为 true）===')
  console.log('port', PORT, 'in use:', await isPortInUse(PORT))

  console.log('\n=== 执行 taskkill /T /F ===')
  spawn('taskkill', ['/PID', String(child.pid), '/T', '/F']).on('close', async () => {
    setTimeout(async () => {
      console.log('\n=== 清理后端口检查（应为 false）===')
      const still = await isPortInUse(PORT)
      console.log('port', PORT, 'in use:', still)
      console.log(still ? '\n❌ 失败：进程树未清理干净' : '\n✅ 通过：进程树已完全终止')
      process.exit(still ? 1 : 0)
    }, 1500)
  })
}, 12000)
```

**验证标准**：

1. 日志中的 ANSI 颜色码**完整保留**（`[OUT]` 输出中可见 `\x1b[32m` 之类）
2. 启动后端口 5173 处于监听状态
3. `taskkill` 之后端口**完全释放**（这是核心，必须为 `false`）
4. 任务管理器中**无残留 node.exe**（手动确认）

## 附录 B：开发期排查「窗口不显示」

Electron 应用启动后看不到窗口，是开发期最容易误判成「代码写错了」的一类问题。
本项目实际踩过一遍，**根因是观察方式，不是产品缺陷**，故把方法论固化下来。

### B.1 先分清两种现象

| 现象 | 含义 |
| --- | --- |
| 主进程崩溃 / 非零退出 | 代码问题（本项目遇到过：宿主注入 `ELECTRON_RUN_AS_NODE=1`，见 §9 第 10 条） |
| 主进程活着、无窗口、无任何报错 | 大多是**加载失败**或**观察工具失真**，未必是代码问题 |

### B.2 打开主进程的诊断出口

设 `TM_DEBUG=1` 后启动，窗口生命周期事件会写入
`%APPDATA%\terminal-manage\debug.log`：

```
[renderer debug] [vite] connected. @ http://localhost:5273/@vite/client:827
[window] did-finish-load
[window] ready-to-show 鈫?show()
```

- **有 `ready-to-show`** → 页面加载并绘制成功，`show()` 已执行，**窗口一定存在**，
  问题出在「怎么观察」而不是「怎么加载」。
- **只有 `did-fail-load`** → 才是真的加载失败，日志里有错误码与 URL。

用文件而不是 stderr，是因为 Windows 上 GUI 进程的 stdout 不一定连得到父终端 ——
实测主进程的 `console.log` 一个字都没看到。

### B.3 三个会让「窗口看起来不存在」的陷阱

1. **`Get-Process` 的 `MainWindowHandle` / `MainWindowTitle` 不可靠。**
   它带缓存，不调 `Refresh()` 就可能返回 0 或空串。同一个进程连续两次查询，
   第一次有标题、第二次为空是常态。**按标题找窗口请用 `EnumWindows` + `GetWindowText`**，
   别信 `Process.MainWindowHandle`。

2. **长驻进程的输出不要用 `| Out-String`。**
   它会把全部输出缓冲到进程结束，等于什么都看不到。
   要落盘就用 `| Tee-Object -FilePath dev.log`。

3. **进程树可能随父进程一起被回收。**
   在受限的宿主/CI/IDE 环境里，父 shell 一退出，派生的 Electron 进程会被连带杀掉；
   反过来，`job_kill` 之类的操作杀掉父进程也**不会**带走 Electron，
   残留实例会继续持有单实例锁，让下一次启动在 `requestSingleInstanceLock()`
   处**静默退出（exit 0、无任何输出）** —— 现象和「窗口打不开」一模一样。

   所以验证 GUI 时，**启动与断言必须在同一条命令里完成**，不要跨命令依赖上一个进程还活着。

### B.4 抓一张窗口截图（窗口被遮挡时）

`CopyFromScreen` 只能抓屏幕最上层的内容，窗口被别的应用挡住就会截到别人的界面。
`PrintWindow` 配 `PW_RENDERFULLCONTENT`（值为 `2`）可以直接向窗口要重绘，
即使它被完全遮挡也能拿到正确内容，对 Chromium/Electron 有效：

```powershell
$bmp = New-Object System.Drawing.Bitmap($w, $ht)
$g   = [System.Drawing.Graphics]::FromImage($bmp)
$hdc = $g.GetHdc()
[WinCap]::PrintWindow($hwnd, $hdc, 2)   # 2 = PW_RENDERFULLCONTENT
$g.ReleaseHdc($hdc); $g.Dispose()
$bmp.Save($out, [System.Drawing.Imaging.ImageFormat]::Png)
```

### B.5 一体化脚本 `spike/shot.ps1`

上面这些零碎步骤各自都要配一遍 `Add-Type`、找窗口、清理，很容易漏掉清理而留下占着单实例锁的 Electron 进程。所以把它们固化成一个脚本 `spike/shot.ps1`（126 行，纯 ASCII），一条命令跑完整个「启动 → 等窗口 → 截图 → 清理」：

```
param: $Out = 'docs\screenshot-m2.png'
       $TitleLike = 'Terminal Manage'
       $TimeoutSec = 60
```

流程：

1. `$env:TM_DEBUG = '1'`，让主进程把窗口生命周期写进 `debug.log`
2. `Start-Process npm.cmd -ArgumentList 'run','dev' -NoNewWindow -PassThru`，并把 stdout / stderr 分别重定向到 `dev.log` / `dev.err`
3. 每 500 ms 用 `Find-AppWindow`（`EnumWindows` + `IsWindowVisible` + `GetWindowTextW`，命中 `$text.Contains($TitleLike)` 即停）轮询找窗口；超时则打印 `dev.log` / `dev.err` 尾部，`taskkill /PID $proc.Id /T /F` 后退出 1
4. 找到后 `Start-Sleep -Seconds 2`，留一帧绘制时间
5. `GetWindowRect` 取尺寸 → `PrintWindow($hwnd, $hdc, $PW_RENDERFULLCONTENT)` → `bmp.Save($outPath, Png)`
6. 打印 `%APPDATA%\terminal-manage\debug.log` 尾部（失败时的第一现场）
7. 清理：`taskkill /PID $proc.Id /T /F`，再 `Get-Process -Name electron | Stop-Process -Force` 兜底

**两条必须记住的坑**：

**(a) 脚本必须写成纯 ASCII。** Windows PowerShell 5.1 在文件没有 UTF-8 BOM 时按 **ANSI** 读取 `.ps1`，中文注释会变成乱码，并让解析器直接失败：

```
源文本中包含无法识别的标记。
字符串缺少终止符: '。
```

这类报错看起来像语法写错了，实际上只是编码问题 —— 与脚本逻辑无关。用 `pwsh`（PowerShell 7）跑也一样，因为文件本身的编码没变。

**(b) 启动与断言必须在同一次调用内完成。** 每条 DSH 命令都跑在自己的进程树里，命令一结束，它派生的 Electron 子进程就被连带回收。所以「先起一个后台进程，下一条命令再去截图」这种写法必然失败 —— 后一条命令执行时窗口早没了。`spike/shot.ps1` 把启动和截图放在同一个进程里，就是为了绕开这一点（另见 B.3 第 3 条）。

> 调用方式：`& .\spike\shot.ps1`（本机 `pwsh` 不在 PATH 上，但这个脚本用 Windows PowerShell 5.1 跑没有任何问题）。

## 附录 C：CSP 在 Electron 里的写法约束

`frame-ancestors` **只对 HTTP 响应头生效**，写在 `<meta http-equiv="Content-Security-Policy">`
里会被浏览器静默忽略，并在每次启动时于控制台留下一条：

```
The Content Security Policy directive 'frame-ancestors' is ignored when delivered via a <meta> element.
```

本项目因此改用 `frame-src 'none'`（meta 中有效，禁止本页嵌入任何子框架）。
至于「本页自己不被别人嵌入」，Electron 桌面应用的窗口由主进程独占，
不存在被第三方站点 iframe 的场景，无需该指令。

另外 `script-src` 必须保留 `'unsafe-inline'`：Vite 在 dev 模式下为每个 `.vue`
文件注入内联 HMR 脚本，限制成 `'self'` 会直接让热更新失效。

### D.2 左栏：分组树

栏头两个入口，打开的是 `NewNodeModal.vue` 的两种**不同模式**，不是同一个弹窗的两副面孔：

| 入口 | 弹窗标题 | 字段 | 校验 | 按钮 |
|---|---|---|---|---|
| **＋项目** | 新建项目 | 项目名称、项目路径 | 两者都必填；空着提交分别报「请填项目名称」「请选择项目路径」 | 创建项目 |
| **＋分组** | 新建分组 | 分组名称（**没有路径字段**） | 名称必填 | 创建分组 |

> 早先这两个入口共用一个「目录可留空」的弹窗，连标题都是靠「用户有没有填目录」反推出来的 —— 从「＋目录」进来、还没选路径时，标题显示的是「新建分组」，看到的和点的不一致。现在模式由调用方显式传入（`mode: 'project' | 'group'`），标题 / 字段 / 校验 / 按钮文案全部跟着模式走。
>
> 项目模式下选完目录会把 `package.json` 的 `name` 预填进「项目名称」，**但只在用户还没自己写过名称时**。填的是真名而不是一个悄悄生效的替身：字段可见可改，所以「项目必须有名称」这条要求没有被绕过，只是省了一次输入。

- 分组可折叠，`GroupNode.expanded` 持久化，省得每次重启都要重新点开
- 每行左侧是状态点：`●` 运行中 / `○` 空闲 / `⚠` 脚本已消失（`missing`）
- **分组行显示后代的聚合状态**，如 `2/3 运行中`（`groupStats()`）—— 不用展开就能知道这一支下面有几个在跑
- 双击就地重命名。**刻意不用 `window.prompt`**：它在 Electron 的渲染进程里不可用（直接返回 `null`），而且弹窗会打断视线
- 右键出 `NodeMenu.vue`，菜单项按节点类型分叉：

| 命令节点 | 分组节点 |
|---|---|
| 启动 / 停止 | 新建命令… |
| 重命名 | 新建子分组 |
| 编辑命令… | 在此新建项目… |
| 在同一分组新建命令… | 重新扫描 package.json |
| 隐藏此命令 / 取消隐藏 | 编辑命令可见性… |
| 标记为常驻命令 / 取消标记 | 重命名 |
| 移动到… | 打开所在目录 / 绑定项目目录… |
| 删除（危险色） | 解除目录绑定 |
| | 移动到… |
| | 删除分组（危险色，连带整个子树） |

> 「标记为常驻命令」在右键菜单里也留了一份，但卡片头上那颗星才是主入口（见 §4.4.4）。留着它是为了不破坏「右键能找到这条命令的全部属性」这个约定 —— 卡片区只有一屏，树里滚到深处的命令照样要能改。

> 「移动到…」的候选目标会排除节点自己与自己的后代 —— 主进程也会拒绝这种移动，但让用户在点下去之前就看不到无效项，比点了报错好。
>
> **「移动到…」是唯一不「执行完就关掉菜单」的项**：它把当前菜单原地换成目标列表（标题变成 `<名字> 移动到…`）。因此它不能复用其余菜单项的 `act()` 路径 —— `act()` 先 `emit('close')`，而父组件是用 `v-if="menu"` 渲染菜单的，整个 `NodeMenu` 会在这项刚要展开子级之前就被销毁。表现是**点了没有任何反应**，不报错、日志里也没有线索，截图同样看不出来（菜单本来就画得对）。菜单项现在用 `keepOpen?: boolean` 声明这类「展开子级而非执行」的行为，由 `runItem()` 分派；界面探针里有一条断言专门守它（§11）。

### D.3 右侧上半区：命令卡片网格

工具栏有两个按钮：**重新扫描**（只对选中的分组有意义）与 **＋ 新建命令**。这一行同时兼作「标题行」：面包屑告诉你当前看的是哪一层，紧跟着是这一层的命令统计（形如 `12 条命令 · 3 隐藏 · 2 已标记`），再往右是 **命令可见性** 按钮 —— 点开就是 D.6 那个勾选弹窗，范围正是这一层。重新扫描完成后顶部出现一条结果提示，形如：

```
重新扫描完成：新增 2 · 失效 1 · 恢复 0 · 更新 3
```

空状态会直接把出路写出来：「点右上角『＋ 新建命令』手写一条，或右键左侧分组『重新扫描 package.json』」。

**卡片是自适应网格**，一行放得下 3–4 张。每张卡片的内容：

```
┌──────────────────────────────────────────────┐
│ ● ⚡ 自动读取                               ☆ │  ← 状态点 + 来源标记 + 标记星
│ dev                                          │  ← 昵称，独占一行（双击改名）
│ npm run dev                                  │  ← 实际命令行，等宽、点击复制
│ [未启动] [:5173] [🔗 2]              employee…│  ← 状态胶囊 + 端口胶囊 + 链接下拉 + cwd
│ [▶ 启动] [重启]               [编辑] [⋯]     │
└──────────────────────────────────────────────┘
```

**卡片头那一行只放「属性」，昵称独占一行**。昵称原先挤在卡片头里、和「⚡ 自动读取」一样大（13px）—— 一屏十几张卡片扫过去认不出哪张是哪张，只能去读命令行里的 `npm run xxx`，而那恰恰是名字要替用户省掉的东西（名字存在的理由就是这个）。抽成独立一行、字号提到 15px 之后，整张卡片从上到下读起来就是决策顺序：属性 → 名字 → 实际命令 → 状态 → 操作。卡片头剩下状态点、来源标记、星标三样都是「这条命令是什么」的属性，星标仍在最右端（`spacer` 顶过去）。长名字仍然**单行省略号**收尾，`title` 里带着全名 —— 不做两行折行是为了十几张卡片高度一致，参差的卡片高度会让扫视时视线来回跳。

页脚刻意只留四个动作。早先还有「复制」和「清空」两个按钮，后来去掉了：复制命令行本来就是点命令行本身（`title` 写着「点击复制」），页脚再放一个是重复入口，去掉后反馈改成命令行右端浮出一小块「已复制」；清空日志在日志面板头部已有，而那是唯一能看见「清空后还剩什么」的地方，摆在卡片上属于离开上下文操作。

**运行状态改变的是整张卡片的底色**，而不是只让左上角那个 8px 的状态点变绿。卡片网格的实际用法就是「扫一眼看谁在跑」—— 一屏十几张卡片时，一个小圆点根本认不出来：

| 状态 | 底色 | 左侧色条 |
|---|---|---|
| `running` 运行中 | 绿色淡染 | 绿 |
| `starting` / `stopping` 启动中·停止中 | 琥珀淡染 | 琥珀 |
| `error` 出错 | 红色淡染 | 红 |
| `idle` / `exited` 空闲·已退出 | 默认底色 | 无 |

色值走主题变量（`--card-running-bg` / `--card-busy-bg` / `--card-error-bg` 等，深浅两套都在 `styles.css` 里），左侧色条用 `box-shadow: inset 3px 0 0` 画出来 —— 不占布局、不引入额外元素。**这三条类名规则在样式表里必须排在 `.card.focused` 之前**：同优先级下后者胜出，否则「运行中且被选中」的卡片会丢掉蓝色的选中边框，而选中决定了下半区日志面板显示谁。

四个可点的元素各有分工：

- **右上角的星标 `☆` / `★`** —— 标记为「常驻」，点「启动已标记」时会被一起拉起（见 §4.4.4）。刻意**常驻显示**而不是悬停才出现：悬停才露出的星标等于没有，用户不会知道卡片能标记；也刻意和来源标记换了位置，放在最右端之后它在每张卡片上都落在同一条竖线上，扫视一列卡片不必左右找
- **端口胶囊 `:5173`** —— 一键打开探测到的那个地址，是最高频的动作
- **链接下拉 `🔗 2`** —— 这条命令输出里出现过的**全部**地址，点一条交给浏览器（见下）
- **右下角的 cwd 标签** —— 在资源管理器里打开这条命令实际执行的工作目录

**为什么两个入口都要有**：端口胶囊只能开一个，而一条命令同时暴露多个地址是常态 —— 前端 dev server 加上 mock 服务、monorepo 里各子包各自的端口。下拉里的候选来自 `store/app.ts` 的 `linksOf(id)`：倒序扫日志缓冲取每行的 `link` 字段（见 §4.3.3），去重后最多 30 条，**最近出现的排最前**；再把 `detectedPort` 派生的 `http://localhost:<port>` 提到首位，并按去掉尾斜杠的形式与日志里的原文去重（`http://x/` 与 `http://x` 是同一个地址）。**候选只来自被监控进程的真实输出** —— `[terminal-manage]` 开头的工具提示行其 `link` 恒为 `null`（启动横幅会把命令行原样回显，命令行文本里自带的地址不算），见 §4.3.4 的「只认被监控进程的真实输出」。

**只有一个候选、且它就是端口地址时不显示下拉** —— 端口胶囊已经覆盖了这个场景，多一个按钮只是噪音。

停止后如果是**意外崩溃**（不是用户点的停止），卡片区和顶栏会给出区分提示 —— 「……意外退出（退出码 1），并非由你手动停止」。这个区分来自 `ExitInfo.stoppedByUser`。

### D.4 命令卡片的三条来源

**卡片本身是同一种，只有来源标记不同**：

| 来源 | 入口 | 卡片标记 | 重新扫描会碰它吗 |
|---|---|---|---|
| 自动读取 | `+ 导入目录` 批量生成（或分组的「重新扫描 package.json」） | `⚡ 自动读取` | ✅ 会 —— 脚本增删改都跟着走 |
| 手动新建 | 分组右键「新建命令…」/ 卡片区「＋ 新建命令」 | `✎ 手动` | ❌ 不会 |
| 手动新建（挑 script） | 新建弹窗里从所属目录的 `package.json` 所列 scripts 里选一条 | `✎ 手动 · dev` | ❌ 不会 |

> 这个标记不只是装饰 —— **`CommandNode.autoDiscovered` 决定了「重新扫描」的边界**：`true` 的卡片可以被脚本的增删改覆盖，`false` 的卡片完全不受影响。所以「自动读取」的卡片改过命令之后会变成手动卡片，从此不再被扫描动到。

### D.5 新建命令的前置条件

命令节点**自己不存路径**，它跑在「最近的带 `path` 的祖先分组」的目录里（`resolvePath`）。因此新建弹窗里：

- **工作目录是只读的**，显示成「继承自 xxx」，让用户明确知道这条命令会在哪跑；
- **整条祖先链都没有绑定项目目录时，直接拒绝创建**：

  - 还没选分组 → `先选中一个分组，命令需要一个工作目录`
  - 分组及其上级都没绑目录 → `这个分组（以及它的上级）都没有绑定项目目录，命令会跑不起来`

  这是刻意的：与其建出一张按不了「启动」的废卡片，不如当场说清楚要先去哪个分组绑目录。

### D.6 隐藏命令

隐藏有**四个入口、一个兜底**，其中前两处打开的是同一个勾选弹窗：

1. **卡片区标题行的「命令可见性」按钮** —— 弹窗里列出的就是**卡片区当前正在显示的那一批**命令（范围跟随左栏选中的那一层），逐条勾选。勾上 = 显示，取消勾选 = 隐藏
2. **项目 / 分组的右键菜单「编辑命令可见性…」** —— 同一个弹窗，范围换成右键的那一层，标题写成「编辑命令可见性 · 项目名」，让用户一眼看出这次改的是哪一层。这一层没有命令时菜单项直接置灰 —— 灰项看得见，点开一个空弹窗则像出了错
3. **节点 / 卡片的 `⋯` 菜单里逐条隐藏**（「隐藏此命令」/「取消隐藏」）—— 单条快捷开关。有了弹窗之后仍然保留：去掉它，藏一条命令就变成两级操作
4. **设置弹窗的「命令可见性」复选框列表** —— 这一份**按项目分段**：段标题是顶层项目的名字，段右侧写着「N 条命令 · M 隐藏」，段内行尾只画这个项目之内的子分组路径。它不跟左栏选中的范围走，用在「那条命令藏在哪个项目里都想不起来了」的时候一次看全 —— 与项目内的弹窗作用域不同，所以两份都留着
5. **`AppSettings.showHiddenCommands`**（设置里的「在分组树里显示已隐藏的命令」）是兜底开关

前两处的弹窗**即时生效**：没有「保存 / 取消」，只有「完成」（正文上方还有「全部显示 / 全部隐藏」）—— 勾选本身就是意图，不用再确认一次，跟设置弹窗里那一块一样。列表每行是「复选框 + 命令名 + 相对当前范围的分组路径」；分组路径只画范围之内的那一段，因为在 `my-app` 里每行都重复一遍它是纯噪音，但 monorepo 里 `packages/web` 与 `packages/admin` 的区别必须留下 —— 那正是两条同名 `dev` 命令的唯一区别。

> **为什么是「勾上 = 显示」而不是反过来**：反过来（勾上 = 隐藏）在命令多的时候更省事，但「勾掉一条」与「它会消失」方向相反，勾错之后看到的是自己刚想留下的那条不见了。顺着动作的方向写，勾错了也看得出来。

被隐藏的命令**整条从树和卡片区消失**（`showHiddenCommands` 打开时则灰显并标「已隐藏」，好让藏起来的还能找回来），配置本身、脚本绑定、已经跑出来的日志全都照常保留、随时能勾回来。没有第 4、5 项兜底的话，用户把命令藏进一个折叠着的分组之后，就再也找不到入口把它放出来了 —— 这是兜底开关存在的唯一理由。

> 早先卡片头上还有一个常驻的「隐藏 / 取消隐藏」小按钮，已经被这个弹窗取代：点一次按钮只能切一条，命令一多就不成立，用户要的是「点按钮 → 弹窗 → 勾选」。`⋯` 菜单里的单条开关作为快捷方式留着。

### D.7 右侧下半区：日志面板

日志面板显示**当前聚焦的命令**的输出，聚焦由「点卡片」或点左栏的命令行切换。它读的是渲染层 `store/app.ts` 里的环形缓冲（每条命令上限 `AppSettings.logBufferLines`，默认 5000 行），ANSI 由 `utils/ansi.ts` 在**造行时**转成 HTML 存在行的 `html` 字段上（不是惰性重算，见 §4.3.3）。字号跟随 `AppSettings.fontSize`。

面板头部有：状态点 + 命令名 + 状态胶囊 + 行数 + **「↗ 打开链接」入口**（这一命令的日志里出现过 URL 时才有，见 §4.3.4）+「清空」。

输出里的 URL 是**可点的**，但产出的是 `data-url` 而不是 `href`（原因见 §4.3.4，真 `href` 会把应用窗口导航走）。日志内容一律经 `ansi_up` 的 `escape_html` 转义后才注入 DOM。

用户往上翻历史时自动跟随会关闭（粘底判定 `scrollHeight - scrollTop - clientHeight < 48`），出现一个「↓ 回到最新」浮动按钮；切换聚焦命令时无条件拉回底部。
