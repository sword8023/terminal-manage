## 0. 先声明:这是一次明确的范围变更

原始设计**刻意排除了自动更新**,两处白纸黑字:

- `electron-builder.yml:3-5` 注释:「这个工具的定位是『自己 + 团队几个人用』,所以不做签名、不做自动更新、不做多平台」
- `docs/技术方案.md:45-56` 的「非目标(明确不做)」表

本方案落地后,**这两处必须同步改掉**,否则文档和代码互相打脸。另外 `docs/技术方案.md:1329` 已登记「没有代码签名」这一已知不足 — 它在本模块里从「首次运行被 SmartScreen 拦一下」升级成了「静默升级可能被拦且失败无提示」,风险等级上升,§10 有对策。

## 1. 三条已定决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **更新源** | 自建静态 HTTP 目录(`latest.json` + `setup.exe`) | 106 MB 的包(`dist/Terminal-Manage-0.1.0-setup.exe` = 111,457,653 B)从 GitHub Releases 在国内拉取慢且不稳;`README.md:40-41` 已经在要求走 npmmirror,说明网络环境有约束。自建源速度可控,且能加镜像回退 |
| **实现路线** | 自研零依赖(`src/main/core/Updater.ts`) | 延续 `electron-store` → `ConfigStore`、`tree-kill` → `killTree` 的既有路线。**更关键的是不改打包结构**:`electron-builder.yml:26-28` 的 `files` 只有 `out/**/*` + `package.json`,而 `package.json` 有 0 个 `dependencies`;引 `electron-updater` 会把它外部化(`electron.vite.config.ts:23,30` 的 `externalizeDepsPlugin`)并塞进 `dependencies`,那就必须改 `files` 白名单 —— 漏了就是「dev 下正常、装完启动即崩」的静默故障 |
| **安装方式** | 静默自动装 + 重启 | `electron-builder.yml:45` 的 `perMachine: false` 决定了装到 `%LOCALAPPDATA%\Programs`,**静默升级不需要 UAC**。这是能自动装的前提 |

## 2. 非目标

| 不做 | 原因 |
|---|---|
| ❌ 差分 / 增量下载(`.blockmap`) | `dist/` 里那个 117,750 B 的 `.blockmap` 是 electron-builder 顺手产出的,只有 electron-updater 会用它。自研要自己实现 bsdiff 式的块级比对,收益(106 MB → 几 MB)只对高频更新才有意义,而本工具更新频率低 |
| ❌ 灰度 / 多通道 | 用户是「自己 + 团队几个人」,一个 `stable` 通道足够。协议里留了 `channel` 字段,将来要加不用改 schema |
| ❌ 自动回滚 | 需要保留双份安装目录 + 引导器,复杂度远超收益。§10 用「保留上一个安装包」兜底 |
| ❌ 强制升级 / 阻止启动 | `minVersion` 只用来把提示文案从「有新版本」改成「必须升级」,不拦启动 —— 拦了就会有人被挡在门外却没有任何自救手段 |
| ❌ macOS / Linux | 与主项目范围一致 |

```
<feedRoot>/
  latest.json
  Terminal-Manage-0.1.1-setup.exe
  archive/
    Terminal-Manage-0.1.0-setup.exe     ← 保留历史版本,装坏了能手动退回
```

### 4.3 源的来源(优先级从高到低)

1. 环境变量 `TM_UPDATE_FEED` — **测试专用**,和 `TM_USER_DATA`、`TM_DEBUG` 同一个思路(`README.md:73-79`)

## 5. 类型与 IPC 契约

### 5.1 `src/shared/types.ts`(追加,并补进 `EnvInfo:268-275`)

```ts
export type UpdatePhase =
  | 'unsupported'   // dev 模式 / 非 win32，不做更新
  | 'idle'          // 本次启动还没检查过
  | 'checking'
  | 'up-to-date'
  | 'available'     // 已确认有新版本，还没下载
  | 'downloading'
  | 'ready'         // 下载完成 + sha256 校验通过
  | 'installing'    // 已 spawn 安装器，本进程即将退出
  | 'error'

export interface UpdateAsset {
  url: string
  size: number
  sha256: string
}

export interface UpdateInfo {
  version: string
  notes?: string
  publishedAt?: string
  /** 当前版本低于它时，UI 文案改成「必须升级」 */
  required: boolean
  asset: UpdateAsset
}

export interface UpdateState {
  phase: UpdatePhase
  /** 当前运行版本，来自 app.getVersion()（注入，便于测试） */
  current: string
  info?: UpdateInfo
  /** 0–1；服务端没给 content-length 时为 null（UI 显示不确定进度条） */
  progress?: number | null
  bytesPerSecond?: number
  /** phase==='ready' 时已落盘的安装包路径 */
  filePath?: string
  error?: string
}
```

`EnvInfo` 追加两个字段,让设置弹窗能显示版本、也让 renderer 能判断「这个构建支持升级吗」:

```ts
version: string    // app.getVersion()
packaged: boolean  // app.isPackaged
```

### 6.2 版本比较(~25 行)

规则:`x.y.z[-prerelease]`,忽略 `+build`。

- 核心段按 `.` 拆、数值比较(**不是字符串比较** —— 字符串比较会得出 `0.10.0 < 0.2.0` 这种结论)
- 缺失段补 0,所以 `0.1` == `0.1.0`
- 有 prerelease 的 < 没有的(`1.0.0-rc.1 < 1.0.0`)
- 两边都有 prerelease 时逐段比:数字段数值比,其余按字典序

⚠️ **不能 `require('semver-compare')`**。`node_modules/semver-compare` 确实存在,但它是 electron-builder 的传递依赖,**不会被打进包**(`electron-builder.yml:26-28`)—— dev 下跑得通、装完启动即崩,又是一次静默故障。

### 6.3 网络层必须用 Electron 的 `net.fetch`,不用 `node:https`

这是本方案性价比最高的一条。`net` 走 **Chromium 网络栈**:

- 自动解析并走**系统代理**(`node:https` 默认完全不读系统代理,企业网/挂梯子的机器直接失败)
- `{ redirect: 'follow' }` 自动跟随 301/302/307(自研 `node:https` 得手写,而自建源用 CDN/OSS 时 302 是常态)
- 复用 Chromium 的证书配置,不用自己接 CA bundle

超时自己控制(5 秒),失败全程静默 + 退避。**不引入任何新的持久化文件**:每个应用启动只检查一次(延迟 10 秒),之后 24 小时一次定时器;feed 不可达的机器每次启动白试一次,代价是 5 秒后的一次静默失败,不值得为它多加一个状态文件。

### 6.4 下载

```ts
const res = await net.fetch(asset.url, { redirect: 'follow' })
if (!res.ok) throw new Error(`HTTP ${res.status}`)
const total = Number(res.headers.get('content-length')) || asset.size
// res.body 是 WHATWG ReadableStream，node:stream 的 Readable.fromWeb() 转到可写流
```

要点:

- **落盘位置 `userData/updates/<version>/`** —— 不用 `temp`。这样它自动跟随 `TM_USER_DATA` 隔离(`README.md:78`),探针能干净地测;也便于「打开所在文件夹」这个兜底入口
- **先写 `.part`,校验通过再 `rename`** —— 沿用 `ConfigStore.save()` 的原子写思路(`src/main/store/config.ts:545-550`)
- **边写边算 sha256**,校验不通过就删除 `.part` 并且**不重试**(重试只针对网络错误,不针对哈希不符 —— 哈希不符意味着包本身或链路有问题,反复重下没意义)
- **进度事件节流到 ~10 Hz**,否则 106 MB 的分片事件会把渲染进程打爆。仓库已经在日志上解过一次同类问题(`src/main/core/LogBatcher.ts`),用同一个思路
- **重试**:网络错误最多 3 次,指数退避(1s / 4s / 9s)
- **不做断点续传**(M2)。理由:哈希是从第一个字节开始流式算的,续传时得先把已落盘的 `.part` 重读一遍喂给哈希才能接着算,正确性容易写错,而 106 MB 在自建源上重下是可接受的。列为 M2 的可选项,不做也不算欠账

### 6.5 安装时序 ⚠️ 最容易写错的地方

```
renderer: update.install({ restartMarked })
  → state='installing'，广播
  → await onDispose()          // 就是 processes.dispose()（src/main/index.ts:275）
  → 写 pending-restart.json
  → await store.flush()
  → spawn(installerPath, ['/S', ...待实测], { detached: true, stdio: 'ignore' }).unref()
  → app.exit(0)
```

**必须用 `app.exit(0)`,不能走 `app.quit()`**。现有退出流程有两处会拦住它:

- `src/main/index.ts:163-169`:开启「关闭到托盘」时 `close` 事件被 `event.preventDefault()` 拦下,窗口只是 hide
- `src/main/index.ts:292-298`:`before-quit` 里 `preventDefault()` → 走 `shutdown()`

而 `shutdown()`(`:271-284`)会再 `dispose()` 一次 —— 已经杀干净的进程树再杀一次没有意义,还多一层「安装器已经在装、旧进程还没退」的窗口期。安装路径要**刻意绕过**这套,自己按正确顺序做一遍。

### 6.6 `pending-restart.json`:一次性的升级后意图

新版本首启时读 `<userData>/pending-restart.json`:

```json
{ "restartMarked": true, "fromVersion": "0.1.0", "at": 1790756434591 }
```

存在且 `restartMarked` 为 true → `processes.startAll(collectMarkedSpecs(store))`(复用 `src/main/ipc/index.ts:74` 那个判据,托盘菜单同一处),然后**立即删掉文件**。

**为什么塞进一个一次性文件而不是 `settings`**:

1. 它是一次性意图,不是用户偏好 —— 进 `settings` 会让「上次升级时勾过」变成永久默认
2. 用户可能勾了之后取消升级、或者升级失败,那个标记就不该留着
3. 它天然被 `TM_USER_DATA` 隔离

## 7. 与既有设计决策的冲突:升级后要不要自动拉起命令

`src/main/index.ts:258-268` 用了 11 行注释解释:**v2 的「随应用启动自动拉起命令」是个坏默认,已经取消**(「打开工具往往只是想看一眼日志或改个配置,却先被一堆 dev server 抢占了 CPU 和端口」)。现在完全由用户手动点「启动已标记」。

而升级必然重启应用 —— 「升级完顺手把你的 5 个 dev server 拉起来」正是它特意废弃的行为。

**所以:安装确认框里那个勾选框默认必须是关的**,文案也别往「省事」上引。用户当前正在跑命令时,确认框要**明确列出正在运行的数量**(「当前有 3 条命令在运行,升级会先停止它们」),让「我点了升级所以进程没了」这件事有预期,而不是变成一次静默的数据丢失感。

## 9. 渲染层

- **`UpdateModal.vue`(新)**:按 `phase` 渲染六种形态 —— 检查中 / 已是最新 / 有新版本(渲染 `notes` 纯文本 + 「下载」)/ 下载中(进度条 + 速率 + 「取消」)/ 已下载(「立即重启并安装」+ 运行中命令数提示 + 默认关闭的 `restartMarked` 勾选 + 「打开所在文件夹」)/ 出错(错误文案 + 「重试」)。`notes` **必须按纯文本渲染,不能用 `v-html`** —— 它来自网络

## 10. 发布侧

### 10.1 `scripts/release.mjs`(新)

```
1. 读 package.json 的 version
2. 校验 dist/Terminal-Manage-<v>-setup.exe 存在（不存在就提示先跑 npm run dist）
3. 流式算 sha256 + 取文件大小
4. 用 TM_FEED_BASE 环境变量拼 url，生成 dist/latest.json

```

**刻意不直接上传** —— 上传目标是你自己的源,硬编码进仓库不合适。脚本只负责产出「可以直接拖上去的目录内容」。

`package.json`(`:8-20`)加脚本:

```json
"release": "npm run dist && node scripts/release.mjs"
```

`dist/` 已在 `.gitignore` 里,`latest.json` 跟着它一起被忽略,不需要额外处理。

`TM_FEED_BASE` 未设置时要**明确报错退出**,而不是生成一个 url 为空的 `latest.json` —— 后者会被客户端当成「有新版本但下不了」,是最难排查的那种故障。
